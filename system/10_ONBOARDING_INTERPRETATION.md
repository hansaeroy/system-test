# 홈페이지 온보딩 해석 규칙

## 목적
계약이 완료된 홈페이지 제작 고객의 온보딩 데이터를 분석하고, 견적·계약 단계에서 확정된 제작 범위를 기준으로 사업 사실을 정리한 뒤, 최소한의 추가질문만으로 실제 기획이 가능한 상태를 만든다.

이 단계의 목적은 디자인이나 구현이 아니라 `확정된 계약 범위 안에서 고객이 제공한 사실을 제작 가능한 정보로 정리하는 것`이다.

## 핵심 원칙

### 1. 사업 사실과 제작 판단을 분리한다.

고객에게 받아야 하는 사업 사실:
- 실제 서비스
- 실제 서비스 범위
- 실제 가격
- 실제 추가비 조건
- 실제 정책
- 실제 운영 지역
- 실제 실적
- 실제 후기
- 실제 인증
- 실제 경력
- 실제 프로세스
- 실제 보증/보완 조건

이 정보는 임의로 만들지 않는다.

제작자가 판단할 수 있는 항목:
- 섹션 순서
- 정보 우선순위
- CTA 배치
- Hero 표현
- 카피 표현
- FAQ 구성
- 이미지 배치
- 디자인 방향
- 레이아웃
- 모션
- 컴포넌트 방식

이 항목은 고객에게 불필요하게 질문하지 않는다.

### 2. 견적·계약 단계에서 확정된 Page Architecture를 우선한다.

견적 또는 계약 단계에서 확정된 `Page Architecture`는 온보딩의 제작 Scope 입력이다. 온보딩에서 다음 값을 새로 결정하거나 임의로 덮어쓰지 않는다.

- `ONE PAGE`: 하나의 페이지 안에서 전체 경험과 전환 흐름을 구성
- `MULTI PAGE`: 여러 페이지로 나누어 구성. 계약서에 페이지 목록·페이지 수·템플릿 범위가 있으면 그 범위도 함께 따른다.

온보딩 분석에는 최소한 다음을 기록한다.

- 계약서의 `Page Architecture` 값
- 그 값을 확정한 견적·계약 출처 또는 버전
- 온보딩 답변과의 Scope 적합성

온보딩 답변은 확정된 구조 안에서 콘텐츠 우선순위, 섹션 순서, 페이지별 역할과 표현 방식을 구체화하는 근거로 사용한다. 구조 자체가 비어 있거나 확인되지 않으면 추정하지 않고 상위 단계의 확인 대상으로 남긴다.

Page Architecture가 입력되지 않았거나 출처가 확인되지 않으면 `ONE PAGE`와 `MULTI PAGE` 중 하나를 선택하지 않는다. 이 경우에는 필요한 상위 단계 확인을 `NEED_INFO`로 기록한다.

### 3. 온보딩 근거가 계약 Scope와 명백히 충돌하면 `SCOPE REVIEW`로 보류한다.

다음처럼 온보딩의 명시적 요구가 계약의 `Page Architecture`로는 자연스럽게 수용되지 않는 경우에만 `SCOPE REVIEW`를 표시한다.

- `ONE PAGE` 계약인데 서로 독립된 목적·전환·운영 흐름을 가진 페이지가 여러 개 필요하다고 명시된 경우
- `ONE PAGE` 계약의 콘텐츠 양이나 기능 요구가 하나의 페이지 경험으로 정리될 수 없다고 판단되는 경우
- `MULTI PAGE` 계약인데 온보딩이 하나의 단일 목적 랜딩페이지만을 명시하고, 계약된 다중 페이지 범위를 사용할 근거가 없는 경우
- 계약에 없는 페이지·템플릿·기능을 온보딩에서 필수로 요구한 경우

단순히 콘텐츠가 많거나, 추가 섹션이 필요하거나, 고객이 `추천해주세요`라고 한 정도는 명백한 충돌로 보지 않는다. 먼저 확정된 구조 안에서 정리한다.

`SCOPE REVIEW`가 되면 다음을 함께 기록하고 최종 기획을 확정하지 않는다.

- 계약상 확정된 Scope
- 충돌을 일으킨 온보딩의 구체적 근거
- 추가되는 페이지·기능·작업 범위의 영향
- 범위 재검토가 필요한 결정

`SCOPE REVIEW`는 온보딩이 자동으로 `ONE PAGE`를 `MULTI PAGE`로 바꾸거나 그 반대로 바꾸는 상태가 아니다. 견적·계약 담당자가 범위를 의도적으로 수정하고 그 변경이 확정된 뒤에만 새 Scope를 기준으로 다시 분석한다.

### 4. 모든 부족한 정보를 질문하지 않는다.
질문은 다음 조건일 때만 한다.
- 사실이 없으면 서비스 내용을 잘못 표현할 위험이 있는 경우
- 사실이 없으면 가격/정책을 잘못 공개할 위험이 있는 경우
- 사이트 핵심 전환 구조를 정할 수 없는 경우
- 공개 시 허위 정보가 될 가능성이 있는 경우

단순히 디자인을 정하기 위해 질문하지 않는다.

### 5. 추가질문은 최대 3개다.
질문 우선순위:
1. 제작을 막는 핵심 사실
2. 고객의 구매 판단에 직접 영향을 주는 사실
3. 공개 시 위험이 있는 사실

3개 미만이면 억지로 채우지 않는다.

### 6. 고객이 "알아서 해주세요"라고 해도 사실을 만들지 않는다.
잘못된 처리:
- 고객이 가격을 안 줬으므로 시장 평균 가격을 작성
- 후기가 없으므로 실제 후기처럼 보이는 가상 후기 생성
- 보완 정책이 없으므로 무료 재방문 정책 생성

올바른 처리:
- 가격은 상담 문의 처리
- 실제 후기 영역은 자료 대기
- 정책은 확인 필요 상태로 표시

### 7. 자료 부족과 정보 부족을 구분한다.

정보 부족:
- 가격이 정해지지 않음
- 서비스 범위가 불명확
- 정책이 없음

자료 부족:
- 실제 사진 미제공
- 후기 캡처 미제공
- 로고 파일 미제공
- 전화번호/URL 미연결

자료 부족 때문에 기획을 중단하지 않는다.

## 상태 판정

### READY
계약 Scope가 확인되고 온보딩 요구와 정렬되어 추가질문 없이 기획 가능

### NEED_INFO
사업 사실 확인이 필요. 최대 3개 질문 생성

### WAITING_ASSETS
기획은 가능하지만 실제 자료가 아직 없음

### MANUAL_REVIEW
계약 범위 외의 법적 문제, 기술 구현 또는 고객 요구 충돌을 사람이 확인해야 함

### SCOPE REVIEW
온보딩의 명시적 요구가 확정된 계약 Scope와 충돌함. 계약 Scope와 충돌 근거를 기록하고, 범위가 의도적으로 수정되기 전까지 최종 기획·제작 브리프를 확정하지 않음

## 온보딩 분석 출력
1. 사업 핵심 요약
2. 주요 서비스
3. 주요 고객
4. 고객의 핵심 문제
5. 고객이 원하는 결과
6. 차별점
7. 신뢰 요소
8. 가격/정책/범위
9. 계약 Scope
10. Page Architecture와 출처
11. 온보딩 요구와 Scope 적합성
12. 주요 CTA
13. 현재 자료 상태
14. 확인이 필요한 사실
15. Status

`SCOPE REVIEW`인 경우에는 다음 항목을 추가한다.

- 계약상 확정된 Page Architecture와 범위
- 충돌하는 온보딩 근거
- 범위 변경 시 예상되는 페이지·기능·작업 영향
- 범위 수정 확정 전까지 보류할 산출물

## 최종기획과 Creative Build Brief의 범위 규칙

최종기획과 `Creative Build Brief`는 계약·견적에서 확정된 Scope를 소비하고 구체화한다. 다음은 확정된 Scope 안에서만 결정한다.

- `ONE PAGE` 또는 `MULTI PAGE` 구조
- 계약에 포함된 페이지·템플릿·기능의 역할과 순서
- 각 페이지와 섹션의 콘텐츠 우선순위
- CTA, 카피, 레이아웃, 이미지, 모션 표현

온보딩 정보가 더 풍부하다는 이유만으로 페이지를 추가하거나, 계약된 `MULTI PAGE`를 임의로 하나의 페이지로 합치거나, 계약에 없는 기능을 Creative Build Brief에 포함하지 않는다. 필요한 콘텐츠를 확정 범위 안에 우선 배치하고, 수용할 수 없는 요구는 `SCOPE REVIEW`로 남긴다.

범위를 바꿔야 하는 경우에는 견적·계약 단계에서 변경된 Page Architecture와 Scope를 의도적으로 확정해야 한다. 그 확정 사실, 출처·버전, 변경된 범위를 온보딩 분석에 반영한 뒤에만 최종기획과 Creative Build Brief를 갱신한다.
